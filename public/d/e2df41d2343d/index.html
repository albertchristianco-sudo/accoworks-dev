Approach

Four load-bearing decisions

Everything else in the plan hangs off these. If one of them bends during implementation, stop and flag it.

01

Semantics sit between vocabulary and the engines

Tenant status vocabulary maps to product-owned semantics; semantics stamp milestones. SLA, rules, dashboards and reports read semantics and milestones — never tenant statuses. A broker can rename or restructure their workflow and the engines never notice.

02

One mutation spine: SQL RPCs

Every shipment mutation goes through security invoker RPCs (RLS applies): state change, milestone stamps and the event append happen in one transaction, with source and actor recorded. Phase 2–4 integrations become additional callers of the same spine — no Phase 1 rewrite.

03

Attention is materialized, not computed on read

attention_item rows reconciled by a rule evaluator. Items need lifecycle (opened, auto-resolve, snooze), stable ordering, and Phase 2+ alerts need edge-triggering — read-time computation can provide none of that. Summary tiles stay computed on read.

04

Copy tdoc conventions — with three exceptions

Copied: @supabase/ssr four-client pattern, session-refresh proxy, timestamped additive migrations with security definer stable RLS helpers, zod server actions, magic-link auth with email→membership linking, check scripts, ephemeral-Docker localdb harness.

Not copied: Postgres enums for workflow statuses (exactly wrong here), the single-tenant role model, and permissive-baseline-then-harden RLS — multi-tenant isolation is strict from migration one.

Design carries forward from the pitch prototype (rail + topbar shell, panel/chip/urgency-bar vocabulary, cobalt/amber/red/green tokens, mono tabular figures, slideover detail, board cards). Its data model — a single 8-stage kanban — is discarded: it cannot carry three status axes, lane, exceptions, location, handler and SLA instrumentation.

Architecture

The contract implementers must not break

C1

Vocabulary is mutable, identity is not

  • Rename = label edit; row identity and history untouched.
  • Add = new row mapped to a semantic.
  • Remove = active=false, never hard-delete — historical events still reference it.
  • sort_order is display/suggestion only; axes are not sequential state machines in v1. Manual ops must be able to correct mistakes freely; the event trail preserves what actually happened.
C2

Every status maps to exactly one semantic

  • One-to-one rather than tag sets — admins must be able to comprehend the mapping screen.
  • *_other absorbs genuinely custom statuses; they then don’t drive milestones or semantic rules — correct behavior.
  • Grouping lives consumer-side as semantic sets in code, e.g. IN_CUSTOMS = {lodged, processing, examination, assessment, payment}.
C3

Milestones stamp once

  • Semantics with a milestone mapping stamp timestamps via apply_status_change — only when null. Re-applying a status never rewrites history.
  • Corrections go through correct_milestone with an audit event.
  • SLA, reporting and the Phase 5 client view read milestones and semantics only.

Why the naive lookup fails, concretely: with label-only statuses, “average release time by lane” requires knowing which status means released per tenant. Every rule and report would need per-tenant status-ID configuration, and a renamed or split status silently breaks SLA computation.

Cross-tenant row attachment becomes impossible at the constraint level, not just the policy level. Cheap now, unretrofittable later.

RLS helpers · security definer stable

app_member_tenant_ids() · app_is_member(t) · app_tenant_role(t) · app_is_owner_or_admin(t) — with the email fallback for not-yet-linked invites.

Indexes that matter

shipment (tenant_id, current_department_id) where closed_at is null · per-axis status indexes · (tenant_id, bl_number) · partial unique on boc_entry_no · (tenant_id, client_id) · (tenant_id, lodgement_at) where actual_release_at is null (SLA sweep working set) · shipment_event (tenant_id, shipment_id, occurred_at desc) · open-exception partial · attention_item partial unique + (tenant_id, severity desc, opened_at) where resolved_at is null · all FKs indexed.

Policy shape — uniform across tenant-scoped tables
  • select — app_is_member(tenant_id)
  • insert — member; vocabulary/settings/rule tables require owner/admin
  • update — member for operational tables; owner/admin for vocabulary, sla_policy, holiday, rule, membership, tenant
  • delete — none on shipment, shipment_event, exception, attention_item, import_batch — append / soft-deactivate model
  • status_semantic — select only, no writes
  • attention_item — select for members; no insert/update for authenticated — written only by the reconciler through service role, plus a column-guarded owner/admin update for snoozed_until alone

Deliberate choice, flagged for Ac: reads are tenant-wide for all members — the whole brokerage works one shared board today, and department-scoped read fences would fight the workflow. Department scoping in v1 is routing (queues, required current_department_id), not access control. Reversible cheaply before S1, expensively after.

Inside the transaction: validate → update state → stamp milestones → append shipment_event with source and actor. Nothing mutates a shipment outside this spine — that invariant is what makes Phases 2–4 additive callers instead of rewrites.

Working/calendar-day math over sla_policy + holidays; semantic-set constants; rule catalog, evaluator and reconciler diff logic — all pure data-in/data-out, with pinned check cases: holiday spans, weekend masks, month boundaries, snooze, idempotent re-evaluation.

Attention engine

Write-triggered, plus swept — reconciled, never recomputed away

Evaluation

(a) On write: every mutating server action evaluates that one shipment against enabled rules and reconciles — synchronous, milliseconds.

(b) Sweep: an idempotent route handler (/api/internal/sweep, CRON_SECRET bearer) evaluates all non-closed shipments per tenant — because time makes rules true with no write. Hourly via Vercel cron; day-granularity SLAs need nothing faster.

Scheduler deliberately swappable to Supabase pg_cron + pg_net hitting the same URL — zero code change.

Reconciler · service-role · src/lib/rules/reconcile.ts
  • Diff findings against open items
  • Insert new — this edge is the Phase 2 alert hook
  • Refresh severity / last_evaluated_at / detail
  • Auto-resolve cleared conditions and closed shipments (condition_cleared · rule_disabled · shipment_closed)
  • Snoozed items stay open but hidden until snoozed_until
  • No dismiss-forever — the product’s contract is that it nags until the condition clears
Determinism

Evaluators are pure and check-scripted against a pinned scenario table including working-day boundaries and holiday spans.

Re-running the sweep with no state change must produce zero writes — asserted in checks.

Uniqueness is structural: partial unique (tenant_id, shipment_id, rule_id) where resolved_at is null.

Surfacing. Owner dashboard: ranked open items (severity, then age) with shipment context and one click to the detail slideover — plus read-computed tiles: arriving containers, vessels not departed, in-customs count, approaching/beyond target, lane counts, open SPS, ready for delivery. Department users see their queue with attention badges. Dashboard-only per Q6 — the edge-trigger sits unused until Phase 2.

VASP adapters · Phase 3

One TS interface — checkEntry(ref) → NormalizedEntryStatus, capabilities — three implementations (InterCommerce, CDEC, eKonek). Priority per Q11: official API → authorized feed → portal automation → manual. Which mode each VASP supports is the Phase 0/3 spike; build the highest-volume VASP first (open item with the client).

Portal automation · the Q11 hard constraint

Headless-browser login cannot run in Vercel functions — separate worker host (small VPS or Fly machine, fixed egress IP). Broker credentials never enter the product database: vasp_credential holds provider, username hint, vault_ref, status, last_verified_at only; secrets live in the worker’s secret store. Rails: per-VASP kill switch; hard stop + owner notification after N auth failures (never risk locking the broker’s real account — that is the accreditation risk); session reuse; every access logged to integration_run; VASP sub-accounts where supported; and written authorization from the broker before any automated login runs — a plan gate, not a plan step.

Phases 2–5 · designed now, built later

Viber, carrier tracking, client-facing view

Viber bot · Phase 2
  • Webhook route handler; structured menu first, free text second (Q5).
  • Identity binding via a linking-code table mapping Viber user id → membership, with tdoc’s rule carried over verbatim: the Viber user id comes from the webhook envelope, never from message content.
  • Writes go through the same RPCs with source='viber' and a narrow operation allowlist.
  • Owner exception alerts subscribe to attention_item inserts — the edge built in Phase 1.
Carrier tracking · Phase 4
  • Source entirely unscoped — an open item with the client (carrier APIs, aggregator, email/EDI advices).
  • The isolating boundary: carrier data is just another integration_event producer writing carrier-axis semantics.
  • container already exists for per-container granularity.
  • No Phase 1 code assumes a source.
Client-facing view · Phase 5
  • The public six-stage view is a pure function of semantics + milestones — already buildable against Phase 1 data.
  • Blocked on the Trackify question resolving (see risk register); no architecture commitment to Trackify is made or needed now.
  • Nothing in Phases 1–4 depends on the answer.
